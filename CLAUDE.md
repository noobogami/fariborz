# CLAUDE.md — Fariborz

Orientation for a fresh chat. Read this, then go straight to the task. Don't re-read the whole codebase to learn "what is what" — it's mapped below.

## What this is

**Fariborz** is an **autonomous AI research/build agent** built in **Laravel**. You give it a goal; it iterates on its own — analyze state → pick ONE next action → execute → store result → repeat until done. It is NOT a chatbot. The **LLM only decides**; Laravel does the executing, storing, limiting, resuming, and tracing. Everything is designed to be **traceable/debuggable** so a supervisor can reconstruct exactly what path the agent took days later.

Default model is a **local, offline Ollama model (`qwen3:8b`)** — so the architecture must make **weak models reliable**, not assume a strong one. A stronger model should only mean *faster*, not *more capable outcomes*.

## The loop (core mechanic)

One planner iteration = **one queued job** (`AdvanceResearchJob`) that re-dispatches itself until the job finishes. The **queue IS the loop** → crash-safe & resumable because all state lives in the DB, never in a long-lived worker. See `app/Application/Research/ResearchOrchestrator.php::advance()`.

Per iteration: build `ResearchContext` (fresh from DB) → preflight guardrails (stop on limit/timeout/cancel) → `Planner->decide()` (LLM returns a `Decision`: a `ToolCall` or `FinishDecision`) → execute tool via `ToolRunner` → store observation → reschedule.

## Supervisor / worker hierarchy (for big tasks)

A job has a **role**: `solo` (original single loop), `supervisor` (decomposes a goal into a task list, delegates), `worker` (does ONE task, reports back), or `reviewer` (a leaf agent that JUDGES one finished task in its own fresh, tiny context — never does the work — and emits a structured verdict via `submit_review`). Started `supervised` from the UI or `StartResearch::handle(..., JobRole::Supervisor)`.

**Control flow is DETERMINISTIC ("blueprint first, model second") — this is the most important design rule.** A weak model is bad at "what should I do next" and will thrash/infinite-loop. So:
- The **orchestrator auto-delegates** every ready task (deps met), independents in parallel. There is **no `delegate_task` tool for the supervisor** — the model never chooses to delegate.
- The supervisor LLM is asked for only bounded things it's good at: **`plan_tasks`** (decompose, tag each task with a capability `tier`) and, as a **FALLBACK only**, **`review_task`** (verify ONE artifact + accept/revise) — used when a Reviewer agent crashed or returned no verdict. It is never asked to decide *when to finish*; see deterministic finish below.
- **Per-task Reviewer agents — the asymmetric review gate.** A finished task (`TaskStatus::AwaitingReview`) goes through: (1) a deterministic **pre-gate** (`ArtifactChecks::verifyOutputs`) that may only REJECT (a declared output file missing/empty → straight back to `Pending`, no reviewer spent — it would be pure waste); (2) otherwise a dedicated **Reviewer** agent is spawned with real tools (`read_file`, `run_command`, `list_files`, …) to judge the rich/subjective part no file-exists check can, moving the task to `TaskStatus::Reviewing`. It records `{verdict, notes, confidence}` via `submit_review`; `ResumeSupervisorOnChildDone` applies it (accept→`Done`, revise→`Pending`+notes appended to the brief) or, on a crash/no-verdict, falls back to the supervisor's own `review_task` WITH the real artifact injected. See `ResearchOrchestrator::autoDispatchReviews()`.
- **Deterministic finish.** Once every task is terminal (`Done`/`Failed`, nothing `InProgress`/`Reviewing`/awaiting review, no ready `Pending` task), the orchestrator assembles the final report **in code** — no LLM finish turn (`ResearchOrchestrator::supervisorAllSettled()` / `finishSupervisorDeterministically()`). This replaced the old "ask the LLM to finish" step, which is exactly what used to loop into empty responses and fail the job.
- **Model availability/cooldown + failure diagnosis.** A failed worker (or reviewer) is requeued/respawned deterministically — never routed to review, since there's no artifact. If the failure looks like an availability error (rate-limit/gateway/timeout/empty completion — `ModelAvailability::isAvailabilityFailure`), that model goes into a short cooldown and the retry (or a reviewer spawn — see `ResearchOrchestrator::pickAvailableTier()`) is routed to an available model instead, no LLM involved. A non-availability failure instead runs one bounded `FailureDiagnosis` turn that decides a corrective guideline for the next attempt, or a clean retry. Knobs: `research.supervisor.diagnose_failures`, `model_unavailable_cooldown`, `reviewer_enabled`, `reviewer_tier`, `reviewer_max_iterations`.
- A finished worker fires an event → `ResumeSupervisorOnChildDone` wakes the parent (works recursively for sub-supervisors).
- **Shared workspace**: every job in a project tree shares ONE sandbox workspace = `root_job_id` (see `ResearchContext::workspaceId()`), so files combine and a served app can be assembled/deployed in one place. This *is* the "blackboard/knowledge doc" — a task can write `notes.md` and later tasks read it.
- **Tasks have `depends_on`** (seq numbers, default = previous task). A task starts only when its deps are **verified (Done)**. Independents run in parallel. **The dep graph is repaired in code, not trusted from the model** (`PlanTasksTool::execute`): deps = the model's explicit `depends_on` ∪ the producer of every file it declares in `inputs` ∪ the producer of every file path literally named in its brief (basename match against earlier tasks' `outputs`); all edges point backward, so it stays a DAG. And if a plan declares **no ordering anywhere** (no `depends_on`, no `inputs` — the weak-model failure mode: every task "independent", so chapter 3 starts before the outline exists), each task falls back to depending on the previous one. Explicit `[]` is only honored as "independent" when the model showed it understands ordering somewhere in the plan.
- **STOP cascades down the tree** (`app/Application/Research/CancelResearch.php` — the single entry point for cancelling, used by the dashboard, the API, and the orchestrator's own cancel guardrail). Cancelling a job cancels every sub-agent under it (workers, reviewers, sub-supervisors, recursively) and resets its in-flight tasks to `Pending`, so nothing keeps burning model calls or writing into the shared workspace after the operator hit stop. Cancellation is DB state, never a queue operation — a queued iteration for a cancelled job returns immediately. Two edges it covers: a sub-agent spawned by an iteration already in flight when the cascade ran is caught on its first turn by `CancellationGuardrail` (`ResearchJob::hasCancelledAncestor()`), and stopping a SINGLE worker releases the task it held (worker → `Failed` and never retried; reviewer → back to `AwaitingReview`) + wakes the parent, otherwise the supervisor parks forever waiting on a child that fires no completed/failed event. Two more things keep the plan HONEST after a stop: (1) the deterministic passes re-read the job's status between spawns (`ResearchOrchestrator::stillRunnable()`, also checked right before the model call) so a cancel landing mid-pass isn't undone by the rest of that pass re-delegating tasks it just reset; (2) the dashboard never shows a task as `in_progress`/`reviewing` when the job that owns it is terminal or the sub-agent holding it was cancelled — `ResearchTask::displayStatus()` reports a display-only `stopped` instead (the row itself is untouched, so a rerun still sees the real state). That covers rows left in flight by jobs stopped before any of this existed.
- **Stall breaker**: a blocked/no-progress action advances the iteration + a stall counter; after `config('research.limits.max_stalls')` (default 6) it stops with a partial report. Supervisors are exempt from the duplicate/repeated-failure guardrails (their control tools legitimately repeat).
- **Adaptive gateway load control (AIMD)** — a closed feedback loop on the LLM gateway's own responsiveness, deterministic like everything else above: `GatewayHealth` (cache-backed, fed by `HealthTrackingLlmClient` wrapping every model call with zero call-site edits) learns a `state` (`unknown`/`fast`/`normal`/`slow`/`degraded`) from a rolling window of call latency + error rate, and turns it into a `concurrencyLimit()` — halved when slow/degraded, +1 when fast ("load it more, a little"), reset to `base_concurrency` after a quiet period. `ResearchOrchestrator::spawnCapacity()` spends that budget against the GLOBAL count of running workers/reviewers (`ResearchJob::scopeActiveSubAgents`, not just this job's own) before `autoDelegateReadyTasks`/`autoDispatchReviews` spawn anything; a pass that has to hold work back records ONE trace event and parks the supervisor with **no model call spent** — a finishing sub-agent (or the budget growing again) wakes it. `OpenAiCompatibleClient` also drops to 1 client-side retry (from 3) while strained, so retries don't triple the load on a gateway that's already struggling. Knobs: `research.gateway_load.*` (`enabled`, `base_concurrency`, `max_concurrency`, `fast_ms`, `slow_ms`, `error_rate_slow`, `adjust_interval_seconds`, `idle_reset_seconds`, `adaptive_retries`), editable live in Settings ▸ "Gateway load control".

## Where things live

- `app/Application/Research/`
  - `ResearchOrchestrator.php` — the loop + supervisor deterministic driver (`autoDelegateReadyTasks`, `autoDispatchReviews`, `finishSupervisorDeterministically`, `pickAvailableTier`, stall breaker, auto-extend).
  - `Llm/ModelAvailability.php` — the availability/cooldown authority (`isAvailabilityFailure`, `markUnavailable`, `inCooldown`, `pickReplacement`). `Planner/FailureDiagnosis.php` — bounded LLM diagnosis of a non-availability worker failure → corrective guideline or clean retry. `Tools/ArtifactChecks.php` — the deterministic pre-gate (`verifyOutputs`) shared by `review_task` and `autoDispatchReviews`.
  - `StartResearch.php` (`handle`, `spawnWorker`), `ContinueResearch.php` (follow-up guidance).
  - `Planner/` — `LlmPlanner` (calls LLM, streams "thinking"), `PromptBuilder` (system + per-turn prompts; **supervisor vs worker prompts branch here**), `DecisionParser`, `ModelRouter` (**per-task model routing** — see below).
  - **One LLM path: the gateway.** Every model call goes through a self-hosted **LiteLLM** proxy (`litellm` + `litellm-db` compose services) fronting local Ollama AND cloud providers behind one OpenAI-compatible endpoint. The app has a SINGLE driver — `OpenAiCompatibleClient` (`app/Infrastructure/Research/Llm/`), bound unconditionally in `ResearchServiceProvider::register()`; there are no per-provider drivers anymore (the old `OllamaClient`/`AnthropicClient` were removed — the gateway does the routing). It's generic, so it also works against LocalAI/vLLM/OpenRouter by changing `research.llm.openai_compatible.base_url` (→ `http://litellm:4000/v1`). Provider API keys live in the **gateway's** DB/env, not the app; the app only holds `services.openai_compatible.key` (the gateway's master key). **Models are managed from Fariborz** — Settings ▸ Tools ▸ "Gateway models" (a form: provider + model + name + key) or `php artisan litellm:seed` — and stored DB-backed in LiteLLM (`store_model_in_db`), not in `services/litellm/config.yaml` (its `model_list` is empty now). The catalog/providers live in `config/litellm.php`; `LiteLLMAdminClient` talks to LiteLLM's `/model/*` + `/health` admin API (add/remove models from the "Add model" form, and an on-demand health check that colors the model chips). **Fariborz never talks to Ollama directly** — Ollama's connection is the gateway's concern (`OLLAMA_BASE_URL` on the `litellm` service); the old `OllamaManager`/pull UI was removed.
  - **Benchmarking a gateway model (evidence, not vibes).** Settings ▸ Tools ▸ Gateway models ▸ "Benchmark" probes a model with `App\Application\Research\Llm\ModelBenchmark`: `ping` (reachability), `envelope` (parses through the REAL `DecisionParser` — this is the exact weak-model failure mode above, so failing it means `broken` regardless of speed or score), `reasoning` (a one-answer ordering question), and — only on a "deep" run — `context` (a needle-in-haystack that specifically detects the `num_ctx` truncation footgun described above; failing only `context` while passing the rest means fix the gateway config, not the model). A local model takes 1-2 min per probe, so this is **async and serialized**: one queued `BenchmarkModelJob` per model, chained (`Bus::chain`) so exactly one runs at a time and benchmarking never measures gateway contention or fights `GatewayHealth`'s load control — and it never creates a `ResearchJob`. Results land in `model_benchmarks` (score/rating/median latency/suggested tier — a hint, never auto-applied) and feed back into the system: `GatewayHealth` calibrates its "slow" threshold per model against the benchmarked median instead of one fixed number (`research.gateway_load.slow_factor`), and `ModelAvailability::pickReplacement` orders candidates by score (skipping `broken` ones) before probing health, so a handover goes to a proven-good model instead of whichever tier happened to come first in config. The ratings now also govern the parts an operator actually touches: (a) every model dropdown (`SettingsController::withModelDropdowns`) annotates each option with score/rating/latency (`— not benchmarked` when there's none), and flags the CURRENT value's field with a notice when it's `broken`, never benchmarked, or its `model_benchmarks` row is older than `research.llm.benchmark_ttl_days` (default 14); (b) Tools ▸ Gateway models has a one-click, reversible **"apply suggested tiers"**: a deterministic preview (`ToolsController::suggestedTierDiff` — highest score per `suggested_tier`, `broken` always skipped, a tier with no candidate left unchanged, rows already matching marked "already correct") that only writes anything when the operator clicks Apply, through the SAME `SettingsService` path the Configuration form uses, busting `ModelCatalog::forget()` afterward — nothing is ever applied automatically on a benchmark run finishing; (c) `ModelRouter::modelForTier()` — the ONE place a tier becomes a concrete model — now fails open around exactly one fact: if the resolved model is rated `broken`, it reroutes to the best-rated live model instead (logged as `model_router.broken_reroute`, and visible per-turn in the trace since `apply()` pins whatever it returns into `research.llm.model`); a low score or `weak` rating is the operator's own choice and is NEVER overridden — only `broken` (a proven inability to produce a parseable tool call) triggers this, and no benchmark data / an unreadable catalogue / nothing better on record all leave the configured model untouched; (d) `ModelCatalog::pickFallback`'s last-resort arm (nothing the operator configured survived) prefers the highest-scored non-`broken` model among the live names over `$names[0]`; (e) a benchmark is invalidated the moment the model it measured changes — `ToolsController::gatewayCreate`/`gatewayDelete` delete that name's `model_benchmarks` row on success, since the same name can end up pointing at a different model/config (the `think`/`num_ctx` footgun above is exactly how this bit a real operator).
  - **Per-task routing (no role→model hardcoding):** `config('research.llm.tiers')` maps `light|standard|hard → model`. When the supervisor calls `plan_tasks` it tags each task with a `tier` (a bounded "how hard is this?" call); the worker for that task runs on that tier's model. `ModelRouter::apply($job)` pins the tier's model into `config('research.llm.model')` each turn (workers read `config['tier']`; solo/supervisor use `default_tier`). A **blank tier model falls back to the global model**, and the result is then resolved against the gateway's LIVE catalogue by `ModelCatalog` (see the model-names footgun below) — `ModelRouter::modelForTier()` is the ONE place a tier becomes a concrete model id; the orchestrator's availability rerouting and the listener both call it rather than re-reading config. With the gateway, tier models are LiteLLM names (`local-fast`/`local-standard`/`local-hard` = offline Ollama, `gpt-4o`/`claude`/`gemini`/`deepseek` = cloud when online) — so a task's difficulty routes it to a local or cloud model. **Reasoning (`think`) is baked per-tier in `services/litellm/config.yaml`**: ON for `standard` (the default / supervisor / most work) and `hard`, OFF only for `light` (trivial mechanical tasks). Hard-won: a weak model (qwen3:8b) with thinking OFF botches the response *envelope* on complex decisions — it emits a tool's args with no `{"action":"tool",...}` wrapper, tripping `invalid_llm_response` until the job fails. Thinking is ~50× slower but necessary for correctness there; only genuinely trivial tasks can skip it. The gateway path also sends `response_format=json_object` (`research.llm.openai_compatible.force_json`, → Ollama `format:json`) so output is always a JSON object. There's no global think flag on the gateway path (unlike the direct `ollama` driver's `OLLAMA_THINK`); tier choice sets it. All editable in Settings. The chosen model+tier is stored in each turn's trace and shown per-turn in the job flow UI (`ResearchTraceReader::turnMeta` → `show.blade.php`).
  - `Tools/ToolRegistry.php` — role-gates which tools each role sees. `ToolRunner.php` — executes with retries/tracing.

## Services & running

In dev the app is often run on the host via `php artisan serve` and the queue via `php artisan queue:work --queue=research` (run **2–3 workers** so parallel sub-agents actually run concurrently).

- Start a job (CLI): `php artisan research:start "<goal>"`. Trace it: `php artisan research:trace <job-id>`.
- LLM driver/model, API keys, limits are all **configurable at runtime via the Settings UI** (`settings` table overrides `config()`), applied per-iteration.

## Footguns (hard-won — don't relearn these)

- **After changing tools/prompts/orchestrator, restart the queue worker** (`php artisan queue:restart` then relaunch `queue:work`) — a running worker holds old code.
- **Gateway model names are ALIASES, not constants — never hardcode one.** Every name (`local-standard`, `qwen3-normal`, …) is something the operator invents in Settings ▸ Tools ▸ Gateway models and can rename or delete at any moment; the instant they do, a literal in config/`.env`/a saved setting points at a model that no longer exists and the gateway 400s **every turn of every job**. So `config('research.llm.model')` now defaults to **blank** (= "whatever the gateway serves") and everything that is about to SEND a model id goes through `ModelCatalog::resolve()` (`app/Application/Research/Llm/`), which swaps a missing name for a live one — preferring another model the operator already configured, else the gateway's first. Two rules it must keep: **"unreadable" ≠ "empty"** (a down gateway or rejected master key tells us nothing, so it fails OPEN and leaves the configured name alone; only a catalogue we really read can declare a name missing), and the catalogue is **short-cached** (`research.llm.catalog_ttl`, 30s) — bust it with `ModelCatalog::forget()` after any add/remove. Settings shows only live names in its dropdowns and flags a stale saved value instead of silently swapping it.
- **Gateway (LiteLLM → Ollama) MUST set `num_ctx` per model in `services/litellm/config.yaml`.** Ollama defaults to ~4k context, which silently TRUNCATES the long worker/supervisor prompts (system prompt + tools + transcript exceed 4k) — the model then never sees the real task and botches tool calls → endless revise loop, while *short* tasks look fine. The direct `ollama` driver set `num_ctx` from config; the gateway path does not unless you put `num_ctx: 16384` in each local model's `litellm_params`. Verify with a needle-in-haystack: a fact at the prompt start must survive a ~10k-token prompt.
- **Sandbox servers must bind a published port (8090–8099)**; `start_server` refuses others. `run_command` is for commands that FINISH (it hard-kills the process tree at timeout) — use **`start_server`** for anything long-lived.
- **Don't let the (weak) model own control flow.** If you're adding supervisor behavior, make the orchestrator decide and give the LLM a bounded sub-task. Free-form "pick the next tool" caused infinite loops.
- **A `write_file` may contain the model's own prompt scaffolding** ("CURRENT STATE"…); `WriteFileTool` strips it. The **supervisor must read the actual artifact** (`read_file`/`list_files`) before accepting a task — don't trust a worker's self-report.
- **Reviewer spawns and the supervisor's finish are deterministic, same rule as delegation** — they're orchestrator-driven (`autoDispatchReviews`, `supervisorAllSettled`), not the model deciding. A reviewer's TIER is resolved in two places that must stay mirrored: `StartResearch::spawnWorker` (the real resolution: `reviewer_tier` override → task's tier → `default_tier`) and `ResearchOrchestrator::reviewerIntendedTier`/`pickAvailableTier` (reasons about that SAME tier before spawning, to route around a cooled-down model) — drift them apart and a reviewer could get routed to the wrong tier silently.
- **A parked supervisor is only ever woken by one of its OWN children finishing** (`ResumeSupervisorOnChildDone`) — never by a global timer or another job. That's why `spawnCapacity()`'s per-supervisor floor exists: if the gateway-load budget were ever allowed to starve a supervisor down to zero live children (e.g. a global budget already spent by another project), nothing would wake it again and it would deadlock forever. Any future change to spawn gating MUST keep "a supervisor with nothing in flight always gets at least 1" — don't let the budget go all the way to 0 for a job with no live sub-agent.
- Keyless web search is unreliable (SERPs block bots); Tavily/Brave/SerpAPI keys make it dependable (Settings UI). Wikipedia is the reliable keyless seed.
- Redis may need a password in this env (`REDIS_PASSWORD`). `CACHE_STORE`/`QUEUE_CONNECTION` are redis.

## Session handoff — supervised-job reliability (continue here)

**Where it stands:** the supervisor infinite-loop is fixed. Root cause was letting the weak model own control flow (it thrashed delegate→blocked→delegate, iteration frozen). Fix = deterministic orchestration (orchestrator auto-delegates ready tasks; `delegate_task` removed from the supervisor's tools) + stall breaker + supervisor exempt from duplicate/repeated-failure guardrails. A later batch pushed further on "make weak models reliable": per-task **Reviewer** agents with real tools replaced eyeballed acceptance (the old "biggest remaining lever" — now done); **deterministic finish** replaced the LLM's own "decide to finish" turn (the exact thing that used to loop into empty responses); and **model availability/cooldown + `FailureDiagnosis`** route a failed or throttled model's retries — and reviewer spawns — to a healthy model automatically. Verified live on a small project: clean completion, dependency ordering, parallel independents, real assembled deliverable, no leak. Also live-verified earlier: shared workspace assemble+deploy, `start_server` published-port guard (8090–8099), write-file prompt-leak strip.

A further batch fixed **dependency-blind plans**: job `a275e88b` decomposed a 5-chapter story well but gave all 8 tasks `depends_on: []`, so every chapter (and the final assembly) launched in parallel with the outline task — the old "omitted deps default to the previous task" fallback never fired because the model sent an explicit `[]`. Fix is deterministic dep repair in `PlanTasksTool` (inputs→producer wiring, brief path scanning, and a sequential fallback for a plan with no ordering signal at all) — see the `depends_on` bullet above. Replaying that exact plan through the fixed tool yields `#2←#1, #3←#2 … #7←#6, #8←[1,3,7]`.

**Known rough edges / next candidates (not yet done):**
- **Weak-model JSON slips** — `{"action":"review_task"}` instead of `{"action":"tool","tool":"review_task"}`. Prompt now warns against it; watch for recurrence / consider tolerant parsing in `DecisionParser`.
- **Duplicate `child_job_id`** was seen on two independent tasks in one run (both showed the same worker id in a snapshot) — worth confirming `autoDelegateReadyTasks` isn't double-assigning under parallel workers; deliverable was still correct.
- **Speed** — qwen3:8b is ~1–2 min/turn, so big jobs take a long time (expected). Not a bug.
- **Recursion (`mode="project"` sub-supervisors)** still exists via `DelegateTaskTool` but the supervisor no longer triggers it (delegation is deterministic/worker-only). If you want big tasks to auto-recurse, add a `complex` flag to `plan_tasks`/`research_tasks` and have `autoDelegateReadyTasks` spawn a sub-supervisor for those.

**To run a live test:** ensure `sandbox`+`ollama` up, restart workers (`pkill -f queue:work` then launch 2–3 `php artisan queue:work --queue=research`), start a supervised job, trace with `php artisan research:trace <id>`. Reference stuck job: `a2658f09-…` (the loop). Reference clean job: `a2663182-…`.

## Human = "Father"

There is exactly one human, referred to as **Father**. `ask_human` is async and NEVER blocks the loop; questions surface in the "Father & Questions" UI. It's a last resort — exhaust the research/build loop first.
